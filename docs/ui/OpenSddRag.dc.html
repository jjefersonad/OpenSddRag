Agent guide

Using OpenSddRag as an AI agent

OpenSddRag is an MCP server that gives you persistent semantic memory and a strict Spec-Driven Development pipeline. You never edit code ad hoc: every change is a change that moves through eight phases, each producing a versioned, embedded artifact. This guide is written for you — the agent — and is the contract you must follow.

01 · remember
Load working context at session start. Never assume you remember.
02 · follow the phase
Do only the work of the current phase. Advance explicitly.
03 · obey the harness
Rules with severity error block you. Stop and report.

Quickstart

Install, initialize the project, and register the MCP server in your client.

# 1. install & start (Postgres + pgvector required)
$ pip install opensddrag
$ opensddrag serve --port 8000
# 2. in your repo: register project + install slash commands
$ opensddrag init
.mcp.json
{ "mcpServers": { "opensddrag": { "url": "http://localhost:8000/mcp", "headers": { "Authorization": "Bearer $OPSR_API_KEY" } } } }

Command and tool names in this guide mirror the prototype; confirm them against your installed server version (opensddrag --help).

SDD workflow

Run the phases in order. Each command reads the previous artifact from memory and writes the next one. Don't skip phases. Don't do the next phase's work early.

Artifact formats

Write artifacts in these exact shapes. The server parses them. If a section is missing, the phase stays incomplete.

proposal.md
## Problem Why this change exists. ## What changes - Bullet per behavior change ## Affected capabilities billing, webhooks ## Out of scope - Explicit non-goals
specs/<capability>/spec.md
### Requirement The system SHALL process webhooks idempotently. #### Scenario: duplicate event - WHEN a duplicate event id is received - THEN it is acked but not processed twice
design.md
## Decisions ### Webhook ingestion Choice: append-only events table Rationale: replay + idempotency ## Trade-offs ## Risks - Risk → Mitigation
tasks.md
## 1. Schema & migrations - [x] 1.1 Create stripe_events table - [ ] 1.2 Add mirror columns ## 2. Integration - [ ] 2.1 Idempotent processor

Harness rules

Rules are project constraints. They're stored in the database and injected into your session when their trigger fires.

Triggers
always — every session
on_spec — while writing specs
on_apply — while implementing
on_verify — during verification
Severity → required behavior
error — hard stop. Don't proceed. Report the violation.
warning — proceed, but log a justification in the trace.
info — guidance. Prefer it.

Agent operating rules

Paste this block into your system prompt or CLAUDE.md.

You are working in an OpenSddRag project. 1. At session start call get_working_context. Treat it as ground truth. 2. Identify the active change and its phase. Do ONLY that phase's work. 3. Before proposing, search_artifacts for related capabilities/decisions. 4. Write artifacts in the documented formats; never free-form. 5. In apply: one task at a time; mark [x] only when code + tests pass. 6. Check harness rules for the current trigger. error = stop and report. 7. Record a trace after every meaningful action (what, why, result). 8. Never edit code outside an active change. If none exists, /opsr:propose.
Design system · v1

Terminal-grade UI

This is the visual language behind the OpenSddRag app. It's dark and dense. Monospace carries anything machine-readable. One green accent marks progress and primary actions.

Principles

Mono = machine
Use Plex Mono for slugs, commands, file paths, status, labels, and metadata. Use Plex Sans for prose and titles.
Green means progress
Green is for done or active states and the single primary action per view. Don't use it for decoration.
Color encodes artifact type
Proposal is amber, spec is blue, design is violet, and rule is green. Keep these mappings the same everywhere.
Borders, not shadows
Surfaces separate with 1px hairlines. Only overlays (modal and search) get shadows.
